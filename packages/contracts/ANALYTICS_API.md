# Аналитика моей точки — согласованный контракт MVP

Согласовано капитаном 2026-10-16. **Сначала публикуется контракт; реализация следует отдельным commit.** Frontend реализует UI самостоятельно. Основной backend — apps/api, источник — неизменяемый журнал, миграция не нужна. Существующий `/summary` не меняется.

## Запрос

`GET /api/v1/businesses/{id}/analytics?days=7` с `Authorization: Bearer <Supabase access_token>`. `id` UUID из `/me`, обязательная owner membership. `days` — целое **7 или 30**, default 7; прочие значения 422. Без JWT401, чужая/несуществующая точка404, стандартный ErrorResponse; серверный сбой503. Сведения других точек не возвращаются.

## Ответ и определения

`AnalyticsResponse`: business_id UUID, days 7|30, timezone="Asia/Almaty", currency="KZT", as_of UTC ISO8601, period_from/period_to местные даты включительно, today_incomplete=true, cards, daily и hourly. Один согласованный snapshot БД для всех агрегатов. Сегодня берётся из серверного времени; текущий день всегда отмечен неполным. Никакого клиентского date/as_of параметра.

`cards`: sales_minor >=0, receipts_minor signed, sales_count >=0, average_ticket_minor >=0|null, outstanding_minor >=0, debtors_count >=0. Все деньги — целые тиыны; количества целые. Средний чек — HALF_UP до целого тиына (0.5 вверх), при count0 — null. Вычисления без float.

`daily`: ровно days элементов ASC по date, включая нулевые дни. `{date,sales_minor,receipts_minor,sales_count,is_partial}`; is_partial=true только сегодня. Суммы daily равны соответствующим cards. `hourly`: ровно24 элемента ASC hour0..23 `{hour,sales_count}`; сумма равна cards.sales_count. Это **часы регистрации действующих продаж** за период, не посещаемость и не фактический приход клиента. Время — Operation.created_at, локально Asia/Almaty.

### Продажи и отмены

Действующая продажа — строка kind=sale без обратной записи reversal_of на момент as_of. cards.sales_minor, sales_count, средний чек, дневные продажи и часы относятся к **одному набору действующих продаж, зарегистрированных в выбранном периоде**. Отмена исключает исходную продажу из её дня/часа, даже если отмена зарегистрирована в другой день. Отмена старой продажи вне периода не уменьшает продажи текущего периода. Период заканчивается сегодня: отмена после as_of не учитывается в текущем snapshot; при последующем чтении ретроспективные значения могут измениться. Отменённая продажа не является отрицательным чеком.

Поступления — сумма receipts_delta_minor **всех движений, зарегистрированных в периоде**, включая доплаты к старым продажам и отрицательные обратные записи в день отмены. Поэтому день может иметь отрицательные поступления; отмена старой продажи даёт отрицательное поступление сейчас, но не отрицательную продажу сейчас. Погашение не увеличивает sales_count/sales_minor. Числитель/знаменатель среднего чека не смешиваются с поступлениями.

Текущий долг — сумма sales_delta_minor-receipts_delta_minor **по всем датам до as_of**, не только за период. debtors_count — число различных ненулевых customer_id с положительным суммарным долгом этой точки. Отмены применяются через существующие обратные записи; данные журнала не изменяются.

`/summary` продолжает показывать движения за день, включая отрицательные sales_delta в день отмены. При отменах его продажи могут отличаться от ретроспективных действующих продаж `/analytics`; поступления и текущий долг согласованы. Frontend должен подписывать метрику «Действующие продажи», объяснять ретроспективные отмены и «Сегодня — неполный день»; не подменять analytics суммой summary.

## Примеры

[analytics-examples.json](analytics-examples.json) содержит полные ответы: пустые7дней; продажа3000/оплачено1000 и доплата500 (тиыны300000/150000, долг150000, count1, средний300000); отмена старой продажи (текущие receipts отрицательные, sales/count0). Это синтетические данные, не живой отчёт точки. После реализации примеры валидируются Pydantic и включаются в общий examples.json; OpenAPI и generated.ts обновляются вместе.

Нельзя выводить прибыль, прогноз, рост%, сравнения чужих точек или выводы о посещаемости. UI — задача frontend. Backend acceptance: отдельная PostgreSQL; old repayment, отмены за границами, пустые данные, local midnight, half-up, изоляция и согласованность графиков/карточек. Общую Supabase не очищать.
