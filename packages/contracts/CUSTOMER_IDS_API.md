# Получение клиентов по UUID для имён в долгах

Контракт зафиксирован **до реализации**, 2026-10-17, от main `1a541ef`.
Добавочное расширение существующего API0.6.2. Никаких миграций и изменения денежных правил.
Публикация этого документа/PR не означает, что работающий Render поддерживает `ids`.

## Запрос

`GET /api/v1/businesses/{id}/customers`, Bearer Supabase access token.
Path `{id}` — UUID выбранной доступной точки, не slug.

Список передаётся **повторяющимся query-параметром** (`style=form`, `explode=true`):

```http
GET /api/v1/businesses/ad6203bc-7320-5b36-982b-135504c5af68/customers?ids=10000000-0000-4000-8000-000000000001&ids=10000000-0000-4000-8000-000000000002
Authorization: Bearer <access_token>
```

Это синтетические ID для примера, не обещание существования этих клиентов на сервере.
CSV `ids=a,b`, JSON `ids=[...]` и `ids[]=...` не являются поддерживаемой сериализацией.
`ids[]=...` — неизвестный параметр, не включает режим `ids`; frontend обязан использовать точное имя.

| Случай | Результат |
|---|---|
| `ids` отсутствует | Прежний поиск `q`, UUID cursor, limit1–100 (по умолчанию50), прежний порядок по UUID и Page |
| `ids=` или `?ids`, пустой элемент среди UUID, невалидный UUID | 422 `VALIDATION_ERROR`; не превращается в выдачу всех клиентов |
| Пустой массив на frontend | Не выполнять запрос, использовать пустой результат локально. В repeated-key query нет отдельного представления массива из0элементов: отсутствие ключа включает прежний список |
| 1–100 значений `ids` | Полная выборка найденных клиентов **только этой точки** |
| Повтор UUID | Одна строка; порядок первого вхождения UUID после разбора. Регистр букв UUID не создаёт разные ID |
| Более100 значений, включая повторы | 422; лимит проверяется **до дедупликации**, весь запрос отклоняется |
| Вместе с `q`, `cursor` или `limit` | 422, даже если `q=` пуст, `limit=50` совпадает с default или cursor пуст. Не игнорировать параметры молча |
| UUID отсутствует или относится к другой точке | Одинаково пропускается, без списка missing/foreign и без сведений о владельце;200 с оставшимися своими строками |
| Нет ни одного совпадения | 200 `{"items":[],"next_cursor":null}` |
| Нет membership выбранной точки | 404 `NOT_FOUND`, как раньше; корректный JWT без доступа не позволяет читать ни одну строку |
| Нет/невалидный JWT | 401. Валидация query может вернуть422 для некорректного запроса до чтения данных |

Порядок `items` — порядок первых вхождений **найденных** UUID в запросе.
`next_cursor` всегда `null` в режиме `ids`: скрытой второй страницы нет, default limit50 не применяется.
Если frontend нужны более100 уникальных UUID, он разбивает их на отдельные группы до100.

## Ответ

Тот же `Page[CustomerResponse]`, те же поля; дополнительных приватных полей, membership,
subject или данных чужого клиента нет. `note`/`contact` — уже существующие поля доступного клиентского ответа.
Баланс считает backend по всему журналу этой точки и клиента: продажи минус поступления,
включая погашения и обратные записи отмен. Все деньги — целые тиыны KZT, без фильтра по дате.

```json
{
  "items": [
    {
      "id": "10000000-0000-4000-8000-000000000001",
      "business_id": "ad6203bc-7320-5b36-982b-135504c5af68",
      "display_name": "Учебный клиент для примера",
      "note": "Синтетический пример",
      "contact": null,
      "balance_minor": 150000
    }
  ],
  "next_cursor": null
}
```

Во втором UUID нет совпадения в выбранной точке; ответ не сообщает причину.
`150000` — долг1500₸ после продажи3000₸, оплаты1000₸ и погашения500₸.

## Подключение Бекзатом

```ts
// customerIds получены из операций выбранной точки; null пропускаем.
const uniqueIds = [...new Set(customerIds.filter((id): id is string => id !== null))];
if (uniqueIds.length === 0) return { items: [], next_cursor: null };
// Для каждой группы <=100; не добавлять q/cursor/limit из общего list helper.
const query = new URLSearchParams();
for (const id of uniqueIds.slice(0, 100)) query.append("ids", id);
// Отправить через общий Bearer API-клиент с AbortSignal.
// GET `/businesses/${businessId}/customers?${query.toString()}`
```

Не терять следующие группы при >100; пример показывает формирование **одной** группы.
Кэш и pending запросы изолировать по user + business + набору UUID; при смене сессии/точки
отменять старые запросы и не применять поздние ответы. Строить map по ID, не по позиции.
При пропущенном UUID показывать нейтральное «Клиент недоступен», не подставлять имя другого клиента.
Баланс клиента нельзя суммировать по строкам продаж: один клиент может встречаться несколько раз.

Перед включением проверить согласованный deployed SHA и наличие query `ids` в
OpenAPI `paths./api/v1/businesses/{id}/customers.get.parameters`. Одной строки версии0.6.2
недостаточно: старый сервер игнорирует неизвестный `ids` и возвращает первую страницу.
До согласованного rollout функция остаётся кандидатом. Frontend этой задачей не переписывается;
обновляются только generated-типы по OpenAPI. Рабочий Render не переключается автоматически.
