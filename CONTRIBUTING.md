# Работа команды через GitHub

`main` — общая версия, которую можно интегрировать и показывать. Отдельную задачу делаем в отдельной ветке и передаём через pull request. После слияния её получают остальные участники. Это договорённость команды; настройки защиты ветки нужно включать отдельно, они не создаются этим файлом.

## Ветки и владельцы

| Роль | Пример первой ветки | Свой файл передачи |
|---|---|---|
| Капитан/backend | `backend/bootstrap-api` | `docs/handoffs/backend.md` |
| Публичный frontend | `frontend/public-showcase` | `docs/handoffs/public-web.md` |
| Кабинет/frontend-каркас | `frontend/app-shell` | `docs/handoffs/seller-web.md` |
| Учёт/frontend | `frontend/voice-ledger` | `docs/handoffs/ledger-web.md` |
| 3D | `assets/venue-models` | `docs/handoffs/assets-3d.md` |
| Flutter/mobile | `feature/mobile-livestock` | `docs/handoffs/mobile.md` (заполняет mobile) |

Имена — примеры веток, а не сообщение, что они уже созданы. Законченную небольшую задачу сливаем и следующую начинаем новой веткой от актуального `main`. Не держать все изменения два дня без интеграции.

Первым проходит PR с общей документацией. Далее в первые два часа: PR капитана со схемами API и PR владельца web-каркаса. Остальные frontend-ветки получают каркас из `main`; временные страницы на контрактных примерах не выдаются за готовую интеграцию.

## Перед новой задачей

Сначала `git status`. Незавершённые изменения сохранить осознанно в своей ветке: проверить и сделать рабочий commit либо попросить AI помочь отделить их. Не выполнять переключение веток и слияние вслепую поверх неизвестных изменений.

При чистом рабочем дереве:

```powershell
git switch main
git pull --ff-only origin main
git switch -c backend/bootstrap-api
```

Последняя команда — пример для капитана. Каждый подставляет ветку своей задачи. `--ff-only` останавливается при расхождении истории; такой результат нужно разобрать, а не обходить принудительным reset.

## Публикация своей задачи

Проверить изменения, обновить свой файл передачи, запустить подходящие проверки. Добавлять в индекс только файлы задачи. Например, после появления API:

```powershell
git status
git diff
git add apps/api docs/handoffs/backend.md
git diff --cached
git commit -m "feat(api): add health and operation schemas"
git push -u origin backend/bootstrap-api
```

Если менялись схемы или документация, добавить соответствующие пути отдельно. Перед commit проверить, что в staged diff нет секретов. Не создавать пустые изменения только ради этой команды.

На GitHub открыть pull request из своей ветки в `main`, описать результат и проверки. Для готовой части капитан проверяет PR и сливает; frontend-каркас дополнительно смотрит его владелец. Приложить скриншот для UI, пример JSON для API, размер файлов и изображение для 3D. Данные реальных покупателей в PR не публикуются.

## Как получить изменения команды

Если продолжаешь существующую feature-ветку, после сохранения своих изменений:

```powershell
git fetch origin
git merge origin/main
```

`git pull` без указания ветки обычно обновляет текущую ветку из её upstream. Ветка `frontend/voice-ledger` не получает новый `main` автоматически только от `git pull`. Для этого и нужен явный merge `origin/main`.

При конфликте открыть конкретные файлы, сохранить обе нужные части и сверить контракт. Не выбирать автоматически «всё ours» или «всё theirs». После исправления проверить приложение и завершить merge. Если непонятно, что конфликтует, передать AI вывод `git status` и задачу разобраться без удаления чужой работы.

После получения кода попросить AI перечитать изменённые документы и передачи. Для нового набора инструкций Codex надёжнее начать новую сессию в папке репозитория; в текущей явно попросить перечитать `AGENTS.md`.

## Передача контекста

Каждый PR обновляет файл своей роли в `docs/handoffs`. Запись содержит реально сделанную работу, фактические команды проверок и следующий шаг. Полезно различать «код написан», «проверено локально», «слито в main» и «опубликовано»: это разные состояния.

Общий API меняется вместе со схемами и потребителями. Если потребитель делает другой участник, указать зависимость и не считать готовым общий сценарий до интеграции. Один владелец редактирует общие web-зависимости/router, один — миграции и API.

Основной процесс основан на [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow). Все шесть человек имеют свои учётные записи и отдельные локальные копии репозитория.
