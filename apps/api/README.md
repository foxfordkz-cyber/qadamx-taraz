# Qadam API — журнал, AI-черновики и «Мал базар»

Версия **0.5.0** добавляет «Мал базар» в основном backend. [Контракт Flutter, endpoints, фото, ошибки и подключение телефона](../../packages/contracts/LIVESTOCK_API.md). Требуется **0004_livestock**, проверенная только на отдельной локальной PostgreSQL. Общая Supabase остаётся на **0003_drafts**, там новая функция ещё не готова; миграцию в этой задаче не применять. Прежние магазин/заявки/журнал/AI продолжают использовать таблицы до 0003. Единый запуск API/web и состав — [TEAM_INTEGRATION](../../docs/TEAM_INTEGRATION.md).

Новые объявления принадлежат проверенному Supabase subject, без membership магазина. Учёт денег не меняется. `LIVESTOCK_DEMO_MODE=true` по умолчанию помечает новые объявления учебными и исключает их из статистики. Фото опциональны: без настроек Storage публикация без них работает. Для upload нужен private bucket и `STORAGE_SERVICE_KEY` только в серверном `.env`; детали policies и ограничения уборки объектов — в контракте Flutter.

Только на собственной **локальной demo** PostgreSQL: `uv sync --locked`, `uv run alembic upgrade 0004_livestock`, `uv run alembic check`, затем `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000`. Для этого запуска настройте DATABASE_URL на локальную demo БД и Supabase Auth env; seed для livestock не нужен. Для очищающего pytest ниже используйте другую, пустую `*_test` БД. Не подставляйте общую Supabase ни в TEST_DATABASE_URL, ни в команду upgrade.

[Передача AI-интеграции frontend](../../packages/contracts/AI_INTEGRATION.md): точный commit и примеры multipart/уточнения/подтверждения для PR #5.

[Подключение команды](../../docs/BACKEND_FRONTEND_CONNECTION.md): проверенные PR #3/#4/#5, запуск, Base URL, публичные env, businessId и результаты независимых проверок.

Python 3.12, FastAPI/Pydantic 2, SQLAlchemy 2, PostgreSQL, Alembic и Supabase JWT/JWKS. Работают клиенты, продажа, частичное погашение, история, открытые продажи, итог дня и отмена ошибочной записи. Опциональный Gemini разбирает текст RU/KK или аудио в черновик. Денежная запись выполняется только отдельным подтверждением продавца; ручной ввод (`draft_id=null`) работает без AI.

## Запуск

Из корня репозитория в PowerShell:

```powershell
cd apps/api
uv sync --locked
# Только если .env ещё не создан:
Copy-Item .env.example .env
# Заполнить .env локально, затем:
uv run alembic upgrade head
uv run python -m app.seed --demo
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Не заменять уже настроенный `.env` шаблоном. Swagger: `http://127.0.0.1:8000/docs`, OpenAPI: `/openapi.json`, API: `/api/v1`. `/health` и `/api/v1/health` проверяют только процесс, не доступность БД/Auth. Без конфигурации health работает, закрытые методы не обходят авторизацию.

Для ограниченного окружения cache можно разместить в игнорируемом каталоге репозитория до `uv sync`:

```powershell
$env:UV_CACHE_DIR = Join-Path $PWD '../../tmp/uv-cache'
$env:UV_PYTHON_INSTALL_DIR = Join-Path $PWD '../../tmp/python'
```

## Переменные и реальные владельцы

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | PostgreSQL URL, например `postgresql+psycopg://USER:PASSWORD@HOST:5432/DB?sslmode=require`; для Supabase — Direct или Session pooler |
| `SUPABASE_URL` | HTTPS URL проекта Supabase |
| `JWT_ISSUER` | Точно `SUPABASE_URL/auth/v1`, без завершающего `/` |
| `JWT_AUDIENCE` | Обычно `authenticated`, сверить с access token проекта |
| `ALLOWED_ORIGINS` | JSON-массив точных frontend origins, например `["http://localhost:5173"]` |
| `TEST_DATABASE_URL` | Отдельная пустая PostgreSQL с именем, оканчивающимся на `_test`; никогда demo/рабочая база |
| `DEMO_OWNER_A_SUB`, `DEMO_OWNER_B_SUB` | Два различных реальных UUID из Supabase Auth |
| `DEMO_OWNER_A_TOKEN`, `DEMO_OWNER_B_TOKEN` | Их короткоживущие access token, только для привязки и smoke-проверки |
| `AI_API_KEY` | Серверный ключ Gemini, только в игнорируемом `.env`; не передавать frontend |
| `AI_MODEL` | Точный идентификатор доступной модели Gemini с audio input и structured output; в этом окружении выбран `gemini-3.6-flash` |

URL с паролем должен использовать percent-encoding специальных символов. Секреты — только в игнорируемом `.env`. Publishable key не является паролем PostgreSQL и не даёт вход в API. Server/service-role key для проверки пользовательского JWT не нужен.

В Supabase создать два подтверждённых пользователя, получить их access token через обычный вход и записать subject/token в `.env`. Затем:

```powershell
uv run python -m app.seed --demo --bind-owners
```

Команда проверяет оба токена по настоящему JWKS, подпись ES256/RS256, issuer, audience, срок, subject, роль `authenticated`, отсутствие anonymous sign-in; subject должен совпасть с указанным UUID. Только после этого добавляет memberships: владельцу A — clothes/food, B — home на каждой площадке. Привязка добавочная, существующие реальные memberships не удаляются. Известные синтетические владельцы старого seed удаляются из учебных точек и не могут быть привязаны этой командой. Без `--bind-owners` seed не создаёт вход для продавцов.

Frontend передаёт `Authorization: Bearer <access_token>`; API не хранит пароли. Истёкший токен обновляет Supabase-клиент frontend, не backend. Старые HS256-проекты нужно перевести на асимметричные signing keys. Ошибка/недоступность JWKS не открывает доступ.

## Работающие методы

| Метод `/api/v1` | Поведение |
|---|---|
| `GET /me` | UUID пользователя и доступные ему точки |
| `GET/POST /businesses/{id}/customers` | Поиск клиентов с текущим остатком / создание клиента |
| `POST /businesses/{id}/drafts` | Текст или аудио → проверенный черновик, без записи денег |
| `POST /businesses/{id}/operations` | Подтверждённая продажа или погашение: вручную либо с `draft_id` |
| `GET /businesses/{id}/operations` | История; `outstanding_only=true` возвращает открытые продажи |
| `POST /businesses/{id}/operations/{operation_id}/reverse` | Исправление обратной записью, JSON `{ "description": "Причина" }` |
| `GET /businesses/{id}/summary?date=YYYY-MM-DD` | Продажи/поступления за местную дату и общий долг сейчас |

Все эти методы требуют JWT, все вложенные — membership. UUID чужой или отсутствующей сущности даёт 404 без раскрытия данных. Списки: `{items, next_cursor}`, `limit` 1–100 (по умолчанию 50); `cursor` — UUID из предыдущего `next_cursor`. Для клиентов поддерживается `q`, для операций `date`, `customer_id`, `outstanding_only`. Не менять фильтры между страницами; для операций `date` — дата исходной строки, а остатки открытых продаж всегда текущие.

Создание клиента возвращает 201. Денежный POST и его повтор возвращают 200. Для создания операции и отмены обязателен `Idempotency-Key`: 1–200 печатных ASCII-символов без пробелов; удобно UUID. При сетевом повторе сохранять ключ. Один ключ в пределах точки с другим нормализованным телом/действием даёт 409 `IDEMPOTENCY_CONFLICT`; повтор возвращает первоначальный ответ с первоначальными остатками. Текущие остатки получать заново из клиентов/истории/summary.

Деньги — JSON-целые тиыны, максимум одной суммы `10_000_000_000` (100 млн ₸). Строки, float, bool, отрицательные/нулевые продажи и погашения не принимаются. Долг требует клиента. Погашение относится к выбранной продаже и не увеличивает продажи. Балансы/created_at от клиента не принимаются. `customer_balance_minor=null` для продажи без клиента.

## Транзакции и схема

Миграции `0001_catalog` → `0002_ledger` → `0003_drafts` создают закрытую схему `qadam`; прежние миграции не переписаны. Таблица `inquiries` теперь обслуживает публичный POST и защищённые GET/PATCH. `new_inquiries_count` — число обращений, созданных за выбранную дату, независимо от последующей смены статуса.

Не публиковать `qadam` через Supabase Data API. Миграции отзывают права у `PUBLIC`, `anon`, `authenticated`. Составные FK не позволяют связать запись с клиентом/продажей другой точки. Trigger запрещает UPDATE/DELETE журнала: исправление — новая обратная строка. Миграции — отдельный release-step, не startup/request hook.

Запись операции и сохранение идемпотентного ответа выполняются одной транзакцией; HTTP-успех возвращается после COMMIT. Membership удерживается `FOR SHARE`. Для MVP финансовые записи одной точки сериализуются `FOR UPDATE` на business; погашение/отмена дополнительно блокируют исходную продажу и пересчитывают остаток. Это упрощает согласованность баланса клиента и гонки ключей; независимые точки могут писать параллельно. Масштабирование блокировок — отдельная задача.

Продажу можно отменить только после отмены действующих доплат. Отменить отмену или повторно отменить запись нельзя. Это исправление учёта, не реальный возврат. Время записи задаёт PostgreSQL в UTC; дневные границы вычисляются в `Asia/Almaty`, полуинтервал `[начало дня, начало следующего дня)`. Общий долг не фильтруется выбранной датой. Отмены могут сделать дневные суммы отрицательными.

Seed повторяемый, insert-only по детерминированным PK, в одной транзакции; не перезаписывает товары/клиентов. Три площадки, девять учебных точек, девять товаров и клиентов. Slug совпадают с шаблоном 3D: `<venue>-demo-<clothes|food|home>`. UUID — в `packages/contracts/demo-seed.json`.

## Проверки

```powershell
uv run python -m app.export_contracts
uv run python -m app.export_contracts --check
uv run ruff check app tests scripts migrations
uv run ruff format --check app tests scripts migrations
uv run pytest -q
```

Обычный pytest без `TEST_DATABASE_URL` пропускает интеграционные тесты. Для полного прогона указать отдельную **пустую** PostgreSQL `*_test` и загрузить env в процесс:

```powershell
uv run python scripts/with_env.py .env.local-postgres -m pytest -q
```

`with_env.py` принимает любой явно выбранный игнорируемый env-файл. Тест проверяет имя/отличие от основной БД, отсутствие схемы и таблиц до старта; применяет миграции, очищает только свою тестовую схему между случаями, после завершения откатывает миграции. На demo эту команду с её URL не запускать. При аварийном прерывании оставшуюся тестовую схему не удаляет автоматически: требуется осознанная подготовка пустой тестовой БД.

Проверяются JWT с настоящими криптографическими подписями через локальный тестовый HTTP JWKS, деньги и изоляция в настоящем PostgreSQL, конкурентные погашения и повторы одного ключа, откат при сбое между INSERT журнала и идемпотентности, отмены, граница полуночи, повтор seed. Тестовые пользователи/ключи не используются сервером в обычном запуске; auth bypass отсутствует.

Для живого Supabase demo после привязки пользователей:

```powershell
uv run python scripts/smoke_manual.py --demo
```

Smoke создаёт **учебную** продажу 3000 ₸ с оплатой 1000 ₸ и доплату 500 ₸, проверяет повторы, `/me`, изоляцию двух реальных пользователей и 401 для анонима. Ключи фиксированы: повтор запуска не добавляет эти операции снова. Созданные строки остаются в demo-журнале, не удаляются. Нужны ещё действующие `DEMO_OWNER_*_TOKEN`.

В этой рабочей копии отдельный локальный PostgreSQL 17.11 расположен в игнорируемом `tmp/postgres`, данные — `tmp/qadam-pgdata-ledger`, порт `127.0.0.1:55432`, demo/test URLs — в `.env.local-postgres`. После перезапуска Windows его можно поднять из корня репозитория: `./tmp/postgres/pgsql/bin/pg_ctl.exe -D ./tmp/qadam-pgdata-ledger -l ./tmp/postgres.log -o "-h 127.0.0.1 -p 55432" -w start`. Бинарники и данные не входят в Git; на другой машине нужен свой PostgreSQL.

Каталог: публичные `GET /api/v1/venues`, `GET /api/v1/businesses?venue_id=&category=&q=`, `GET /api/v1/businesses/{slug}`. Списки возвращают items/next_cursor, цены — целые price_minor. Публичный POST `/businesses/{id}/inquiries` принимает InquiryCreate и возвращает только id/created_at; повтор client_request_id с другим телом — 409. Лимит 20 новых заявок/точку/минуту проверяется в PostgreSQL под блокировкой. Приватные GET и PATCH заявок требуют JWT/membership и проверяют принадлежность UUID. Деплой не выполнен. Методы и примеры — в `packages/contracts`, результаты — в `docs/handoffs/backend.md`.

## AI: текст, затем аудио, затем подтверждение

Перед запуском этой ветки применить `0003_drafts` к выбранной БД отдельной командой миграции. На выделенном Supabase `qadam-demo` она применена и проверена 2026-10-15 после review; существующие данные сохранены, доступ anon/authenticated закрыт. На новой БД по-прежнему нужен `alembic upgrade head`. Не перезаписывать действующий `.env`; добавить только `AI_API_KEY` и `AI_MODEL`. Без них `/drafts` возвращает 503 `AI_UNAVAILABLE`, журнал продолжает работать.

В Swagger авторизоваться через Bearer и отправить `POST /api/v1/businesses/{id}/drafts` как `multipart/form-data`: ровно одно поле `text` (1–4000 символов после trim) или `audio` (файл), необязательное `locale=ru|kk|auto`. Пример текста: «Продал товар на 3000, Асқар заплатил 1000». `kk` — код казахского языка в контракте; `auto` допускает смешанную речь, вопросы по умолчанию на русском. Дубли полей, URL вместо аудиофайла и неизвестные поля отклоняются.

Поддержаны WAV, WebM/Opus, Ogg/Opus, MP3, M4A/MP4, FLAC. Максимум 8 MiB и 30 секунд **декодированного** аудио (одна аудиодорожка, без видео, mono/stereo, 8–192 kHz). PyAV из locked wheel содержит FFmpeg-библиотеки; отдельный ffmpeg CLI не требуется. Сервер проверяет контейнер и MIME, декодирует с ограничением длительности и передаёт Gemini PCM WAV 16 kHz mono. Запись не сохраняется после запроса и не отправляется в Files API. Ошибки: 413 `AUDIO_TOO_LARGE`, 415 `AUDIO_UNSUPPORTED`, 422 `AUDIO_TOO_LONG`. UI предлагает текст или ручную форму.

Gemini получает только текущую фразу/аудио и схему извлечения. Ключ передаётся заголовком серверного запроса на фиксированный Google endpoint, не в URL. Клиенты, UUID, балансы, JWT и доступ к БД модели не передаются. JSON и деньги проверяются Pydantic; неизвестная оплата остаётся `null`, ноль допустим только при явном долге. Неопределённость возвращается через `missing_fields` и `questions`; пустое поле не заменяется догадкой. Дубли/отсутствие клиента требуют выбора или создания; погашение всегда требует выбора продажи. Backend ищет до 20 кандидатов только в своей точке; для полного поиска frontend использует существующие списки клиентов/открытых продаж. Нечёткий поиск и автоматическое объединение имён не выполняются.

Один общий deadline AI — 25 секунд, включая максимум один повтор невалидного JSON/схемы. Сетевые ошибки и квота не повторяются автоматически: 503 `AI_UNAVAILABLE`; timeout — 504 `AI_TIMEOUT`. Сообщения провайдера, ключи и содержимое ввода не попадают в HTTP-ошибку. UI сохраняет введённые данные в форме и позволяет ручное подтверждение с `draft_id=null`; сервер не создаёт мок вместо ошибки.

Срок действия черновика — 30 минут от сохранения по часам PostgreSQL. Для подтверждения отправить существующий `SaleCreate` или `RepaymentCreate`, дополнив `draft_id` и `Idempotency-Key`. Продавец может исправить все поля, окончательные денежные правила проверяются заново. Порядок блокировок: membership → business → draft → sale. Чужой автор/точка/UUID — 404; истёкший — 409 `DRAFT_EXPIRED`; использованный с новым ключом — 409 `DRAFT_USED`. Повтор исходного ключа/тела возвращает прежний результат даже после истечения срока, но только автору черновика. Потребление, операция и идемпотентность атомарны. Автоматическая очистка старых черновиков пока не настроена; expiry запрещает подтверждение, а не удаляет запись.

Детерминированные тесты используют настоящий PostgreSQL и подписанные тестовые JWT, **Gemini заменён заглушкой**. Проверяются ошибки/timeout, tenant и автор, TTL, гонки, rollback, ручной fallback и реальные аудиоконтейнеры с синтетической тишиной. Тесты не доказывают качество распознавания речи.

Живой разбор учебных RU/KK/mixed фраз запускается отдельно (без подключения к БД):

```powershell
uv run python scripts/smoke_ai.py --live --ids ru01 kk01
# Все 20 учебных текстов; 13 секунд между запросами, остановка при сбое провайдера:
uv run python scripts/smoke_ai.py --live
# Аудио из локального файла, только если его разрешено отправить провайдеру:
uv run python scripts/smoke_ai.py --live --audio path/to/sample.wav --mime audio/wav
```

Этот smoke проверяет извлечённые поля, а не matching клиентов или подтверждение. Для аудио можно задать `--expected-total-minor` и `--expected-received-minor`; без них проверяется только успешный валидированный ответ, не смысл. Он не включает тариф/биллинг и не печатает ключи. Живое аудио и реальные телефонные записи оцениваются отдельно; результаты и ограничения записаны в handoff. API модели: [generateContent](https://ai.google.dev/api/generate-content), [structured output](https://ai.google.dev/gemini-api/docs/structured-output), [аудио](https://ai.google.dev/gemini-api/docs/audio).

Полный живой HTTP-сценарий на выделенной demo-БД:

```powershell
uv run python scripts/smoke_draft_flow.py --demo
```

Нужны `0003_drafts`, настроенный Gemini и действующие реальные `DEMO_OWNER_A/B_TOKEN` с соответствующими subjects. Скрипт поднимает собственный Uvicorn только на loopback, проверяет JWT/memberships, создаёт живой черновик из учебного текста, отдельно подтверждает продажу, читает журнал/summary и проверяет повторы. Затем завершает только свой процесс сервера. Заглушек и обхода авторизации нет. В `mart-demo-food` остаётся **одна учебная продажа 3000 ₸ / получено 1000 ₸ / долг 2000 ₸**. Фиксированный Idempotency-Key не позволяет повторному запуску добавить продажу: следующий запуск сообщает `replay-only`, а не новый live Gemini PASS. Скрипт не удаляет записи и не запускает pytest/очистку на Supabase. Итоговый HTTP-сценарий проверен; браузерный UI и HTTPS-деплой остаются отдельной интеграцией.
