## Что установлено о RU timeout

Две прежние ошибки достигли общего deadline 25 с **на Responses/extraction после успешной STT**, а не при декодировании аудио. HTTP 429 не наблюдался. Старые транскрипции намеренно не сохранялись, поэтому точное побайтовое воспроизведение старого запроса невозможно.

Для новой диагностики разрешённая RU-запись транскрибирована один раз; этот же полученный текст в памяти отдельно направлен в extraction. Модель `gpt-6-luna`, `reasoning.effort=none`, output cap2048, locale auto, один и тот же JSON3325байт/75символов входного текста. Эталонные суммы в запрос не добавлялись.

| Проба | STT, с | Extraction, с | Всего, с | Результат |
|---|---:|---:|---:|---|
| RU audio → STT → extraction | 1.578 | 2.937 | 4.594 | 3000/1000 ₸ верно |
| Та же STT-транскрипция → extraction | — | 10.000 | 10.016 | 3000/1000 ₸ верно |

Детерминированный сбой не воспроизведён. Размер запроса невелик, доказательств ошибки декодирования/конфигурации или необходимости увеличить deadline нет. Различается время ответа одного extraction-пути; первопричина внутри провайдера не установлена. **Timeout не объявлен исправленным** только потому, что последующие вызовы прошли.

Исправлена наблюдаемость: в allowlisted stage-логах появились `request_body_bytes` (из фактического Content-Length сформированного запроса) и `input_chars`; provider/model/status/duration/usage остаются. Нет ключей, JWT, текста, аудио, имени файла или полного ответа. Тест подтверждает равенство extraction-запросов для аудио и той же транскрипции, а также точность/приватность метрик. Общие 25 с не изменялись, автоматических повторов не добавлено.

## Смысл операции и повтор трёх записей

Шесть новых целевых синтетических текстов проверили RU/KZ отрицание оплаты, mixed неизвестную оплату, тиыны (30₸50тиын/10₸25тиын →3050/1025minor), погашение с отрицанием новой продажи и доллары. Первые пять совпали с эталоном. В исходной пробе долларов суммы уже были `null`, но `kind=sale` вместо ожидаемого `unknown`; небезопасной конвертации не было. Уточнена только OpenAI-инструкция: явно неподдерживаемая валюта →unknown/null и уточнение человеком, без пересчёта. Целевой повтор прошёл. Нейтральная STT-инструкция дополнена сохранением отрицаний/валюты/сумм; Gemini prompt и денежный журнал не изменялись.

После изменения ещё раз проверены RU «не заплатил» →received0 и mixed «не знаю, оплатил ли» →received null: оба PASS,2.141/1.906с. Нулевую и неизвестную оплату нельзя подменять друг другом. Проверки моделей остаются выборочными, не доказывают отсутствие любых ошибок речи.

Все новые живые вызовы — OpenAI через серверный адаптер без БД: **0 созданных клиентов,0 сохранённых черновиков,0 денежных операций**. Учебное имя остаётся только query, выбор клиента делает человек. Новый телефонный микрофон/полный browser→HTTP→confirmation не проверялся.

## Расход и защитный резерв — разные величины

- Фактическое списание по billing **не получено**; два прежних прерванных Responses без usage имеют неизвестную стоимость. Она не считается нулевой.

- С начала разрешённых проверок28 pipelines. Сумма доступных оценок **$0.00858611**, но это не полный счёт из-за двух прежних неизвестных этапов и возможного billing rounding.

## Конкретный режим для защиты

Рекомендуемый **основной AI-сценарий — текст** RU/KZ/mixed, `AI_PROVIDER=openai`, точная модель `OPENAI_MODEL=gpt-6-luna`. Подготовленный STT-кандидат для всех трёх языковых вариантов — `OPENAI_TRANSCRIPTION_MODEL=gpt-transcribe`; mini STT не делать общим вариантом для KZ/mixed. Из-за наблюдавшейся ошибки оплаты не полагаться на голос как на единственный основной сценарий защиты: если показывать голос, обязательно сверять каждую сумму/оплату и смысл с человеком до подтверждения. Никакой автоматический выбор клиента/денежный action не добавлен.

Конфигурация после отдельного согласования включения (в серверном игнорируемом env, ключ уже существует; его значение не заменять):

```dotenv
AI_PROVIDER=openai
OPENAI_MODEL=gpt-6-luna
OPENAI_TRANSCRIPTION_MODEL=gpt-transcribe
AI_FALLBACK_OPENAI=false
AI_PRIMARY_TIMEOUT_SECONDS=8
```

`AI_PRIMARY_TIMEOUT_SECONDS` не используется в явном OpenAI-режиме с fallback off. **25с — общий server deadline** для STT+extraction; декодирование/доставка/сохранение вне этого AI deadline. Нет автоматического paid retry, fallback или расширения ожидания. При timeout503/504/невалидном ответе показывать понятную ошибку и сохранять форму, не подставлять нули. Предлагаемые тексты для владельца frontend, не новая UI-реализация:

- RU: «AI не смог подготовить черновик. Введите продажу вручную и проверьте сумму, оплату и клиента. Деньги ещё не записаны».
- KZ: «AI нобай дайындай алмады. Сату сомасын, төленген соманы және клиентті тексеріп, қолмен енгізіңіз. Операция әлі тіркелген жоқ».

Если ответ содержит поля, проверить валюту KZT, отрицания и тип sale/repayment, сумму/оплату; неизвестную оплату оставить пустой для уточнения. Клиента выбрать из своей точки. Только отдельная кнопка подтверждения вызывает существующий журнал с одним сохранённым ключом/телом. Если неоднозначен уже **денежный POST**, сначала recovery/replay того же ключа, а не новая ручная продажа. Ручной ввод остаётся полноценным запасным сценарием защиты. Новый внешний HTTP/UI acceptance после окна ещё нужен; результаты модели не подменяют его.
