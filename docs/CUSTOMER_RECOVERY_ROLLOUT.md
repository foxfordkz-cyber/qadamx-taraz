## Результат review

| Область | Проверенное поведение |
|---|---|
| Атомарность | INSERT клиента и receipt выполняются одной Session/транзакцией; flush обоих, COMMIT до201. Ошибка между INSERT откатывает оба. |
| Конкуренция | Transaction advisory lock по action/business/subject/key работает в PostgreSQL, не в памяти worker. READ COMMITTED позволяет следующему запросу увидеть закоммиченный receipt после ожидания. Полный PK проверяется отдельно: коллизия hash только добавляет ожидание. |
| Replay и конфликт | Hash всех валидированных полей после trim/defaults; порядок JSON не влияет. То же тело → исходный201/ID, другое валидное тело →409 без вставки. |
| Membership | JWT subject задаёт creator; current owner membership проверяется до create/replay/lookup. FOR SHARE удерживается до конца транзакции, конкурентный отзыв ждёт COMMIT. Отзыв запрещает replay/lookup, восстановление membership возвращает доступ к прежнему receipt. |
| Recovery | GET читает только committed receipt текущего автора/точки. not_observed допустим во время незавершённого POST и не разрешает новый key. Проверены потеря HTTP-ответа, поздний worker, новый экземпляр приложения. |
| Retention | Нет TTL, удаления или переназначения ключей. Составной FK не позволяет связать receipt с чужой точкой или удалить его клиента. Snapshot остаётся первоначальным после изменения долга. |
| Legacy | POST без ключа сохраняет201CustomerResponse и допускает отдельные совпадающие клиенты. Задним числом добавить recovery старому POST невозможно. |
| Прямой доступ | Новая таблица с RLS; PUBLIC/anon/authenticated лишены прямых прав. Доступ через основной FastAPI. |

Критичных дефектов в самой операции создания/recovery при review не найдено. Обнаружен **операционный риск отката**: прежний API0.6.1 игнорирует Idempotency-Key, поэтому поздний keyed retry после простого отката создаст дубль. На локально восстановленной копии это воспроизведено. Исправлен план отката и добавлен проверенный защитный entrypoint; обычный запуск0.6.2 его не включает.

## Откат приложения без потери данных

**Не делать `alembic downgrade` и не восстанавливать старый dump поверх работающей БД.** Downgrade уничтожит receipts, restore потеряет новые операции после snapshot. Сохранить схему0006 и все данные; прежний API читает совместимые таблицы, но raw0.6.1 нельзя открывать для customer POST после начала recovery.

Подготовлен `apps/api/scripts/legacy_customer_guard.py`: он загружает явно указанный старый checkout0.6.1 и возвращает503 `CUSTOMER_RECOVERY_PAUSED` на **все** customer POST (с ключом и без) и recovery lookup. Так нельзя обойти защиту fallback-запросом без ключа. Receipt не удаляется;503 не означает not_observed. GET customers, Auth, Analytics, журнал и другие маршруты проходят через прежний API без изменения правил. CORS ограничен сохранённым списком origins, ошибки no-store.

```powershell
# Выполнять только в согласованное окно rollback и после проверки свободного порта.
# Процесс получает DATABASE_URL и прежний ALLOWED_ORIGINS из безопасного окружения.
python <PR22-apps/api/scripts/legacy_customer_guard.py> `
  --legacy-api-dir <подтверждённый-ca51bbf/apps/api> --port 8018
```

Скрипт привязывается только к127.0.0.1 и отказывается загружать версию, отличную от0.6.1. Не запускать старый Alembic против ревизии0006. Когда0.6.2 снова готов, вернуть новый API на ту же БД: исходные keys/receipts продолжат работать. Не отменять неизвестные intents на клиенте и не превращать их в новую запись.

**Репетиция на восстановленной локальной копии:**0.6.2 создал клиента/receipt → raw0.6.1 при прежнем ключе действительно создал второго клиента (риск воспроизведён только локально) → guarded0.6.1 заблокировал keyed/legacy POST и lookup, сохранил GET/Auth/Analytics →0.6.2 вернул исходный receipt и не добавил клиента. Использовались TestClient и синтетические подписанные JWT с локальным JWKS. Это не приёмка общего HTTP. Две синтетические записи репетиции остались только в приватной restore DB; в Supabase ничего не создавалось.
