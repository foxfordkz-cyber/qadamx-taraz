## Вывод по каждому PR

**PR61:** блокирующих дефектов не найдено. Контракт повторяющихся `ids` до100,
business membership, одинаковый пропуск чужих/отсутствующих UUID, серверные
балансы и прежний путь без ids проверены. Полный [review и план Render/отката](CUSTOMER_IDS_ROLLOUT_REVIEW.md)
остаётся действующим; новые server runtime changes при объединении отсутствуют.

**PR63 — состояния истории:** блокирующих дефектов в представленном diff не найдено.
Первичная загрузка/ошибка/успешный пустой список разделены. Догрузка не скрывает
старые строки; кнопка блокируется на время запроса. Ошибка следующей страницы
имеет отдельный retry с тем же cursor, `cancelRefetch:false` не запускает новый
параллельный GET. RU/KZ добавлены в общий словарь ledger; финансовые суммы не
пересчитываются в UI. Query keys прежние: auth scope + business + параметры;
старые данные не переносятся в новый контекст. На disabled Demo query не выводится
ложный успешный пустой API-результат. Внешний формат запросов не изменён.

Эта **готовая часть истории совместима с прежним API и может оцениваться/выпускаться
отдельно**: она не использует ids и не требует rollout PR61. Текущая задача сама
по себе не выполняет production push.

**Имена в долгах/истории — ещё не реализованы в PR63.** `Debts`/`History` продолжают
использовать `useCustomers("")`. Три name-теста для клиента51 явно skipped; это
не PASS и не доказательство исправления. Простое объединение PR61+63 не подключает
ids к UI. Контракт уже опубликован, следующая работа — подключение исполнителем
frontend, а не ожидание проектирования backend. Старый gateway всегда добавляет
q/limit50; отдельный ids read не должен наследовать эти параметры.

   существующих клиентов, не создавать денежные операции/memberships ради проверки.
3. Исполнитель frontend подключает [CUSTOMER_IDS_API](../packages/contracts/CUSTOMER_IDS_API.md):
   группы≤100, пустой набор без запроса, map поUUID, scope user/business/IDs,
   AbortSignal/поздние ответы, нейтральное имя при отсутствии результата. Сохранить
   generated.ts PR61. Нельзя трактовать первую страницу старого API как ids-ответ.
4. Совместно проверить новый **точный frontend SHA**, уже включающий этот read:
   имена в долгах, фильтре клиента и истории после прямого открытия/reload с пустым
   cache; клиент за первой50, несколько пачек, ошибки, смена точки, logout A→B.
