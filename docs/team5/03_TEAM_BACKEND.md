# Задание капитану на весь backend

Твой результат — один работающий FastAPI API с PostgreSQL, авторизацией, голосовым разбором, денежным журналом и заявками. У остальных участников нет отдельных backend: они используют твой контракт. Срок — 24 рабочих часа за два дня, включая интеграцию и резерв.

## Зона ответственности

Ты владеешь `apps/api`, миграциями, seed, server environment, схемами `packages/contracts` и публикацией API. Стек: FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, PostgreSQL/Supabase, Supabase Auth, Gemini через один адаптер. Не начинай с обучения собственной модели: за этот срок нужна проверенная обработка речи с контролем результата.

Все формы, методы и денежные правила — в [контракте](02_ARCHITECTURE_API.md). Этот файл задаёт порядок реализации, а не другую версию API.

## Первые два часа

1. Сверь текущий GitHub; создай структуру API без перезаписи чужих изменений.
2. Проверь реальный AI-ключ, аккаунт хостинга, Postgres и Auth. Сделай минимальный запрос к AI до большой разработки.
3. Создай схемы `SaleCreate`, `RepaymentCreate`, `DraftResponse`, `OperationResponse`, `SummaryResponse`, `InquiryCreate`, `ErrorResponse`.
4. Подними `/health`, OpenAPI и начальный деплой. Передай всем базовый URL и список переменных. Секреты передаются отдельно от Git.
5. Создай девять учебных точек, двух владельцев для проверки изоляции, несколько товаров и покупателей. Раздельные владельцы обязательны даже если основное демо идёт от одной точки.

К концу второй рабочей отметки frontend получает примеры ответов. Ему не нужно ждать полного AI или готовности моделей.

## Порядок реализации

| Рабочие часы | Работа | Проверяемый результат |
|---|---|---|
| 0–2 | Схемы, доступы, каркас, начальная публикация | OpenAPI доступен команде |
| 2–7 | Авторизация и журнал: продажа, погашение, остатки, идемпотентность | К шестому часу ручная продажа проходит до БД; к седьмому — основные ограничения |
| 7–10 | Аудио/текст → AI → проверенный черновик | Живая фраза возвращает поля без записи денег |
| 10–12 | Публичные каталоги, заявки и статусы | Заявка из витрины появляется у владельца |
| 12–16 | Интеграция с тремя frontend, отмена записи, пограничные случаи | Главный сценарий работает целиком |
| 16–19 | Проверки изоляции, конкуренции, дублей и отчётов | Критичные тесты проходят |
| 19–21 | Деплой, таймауты, лимиты, проверка телефона | Рабочая HTTPS-ссылка |
| 21–23 | Резерв исправлений; дополнительные методы только при отсутствии ошибок | Стабильное демо |
| 23–24 | Репетиция защиты и фактические результаты | Ты можешь объяснить роль AI и формулы |

Это рабочие часы, не призыв работать без сна. Ко второй половине второго дня не начинать новую интеграцию.

## Непереговорные правила журнала

Деньги — целые тиыны. Backend считает баланс сам. Долг требует клиента. Погашение связано с конкретной продажей и не превышает её остаток. Повтор запроса не создаёт дубль. Погашения и отмены выполняются под блокировкой исходной продажи. Исправление добавляет обратную запись, не удаляет историю.

Разбор AI и запись операции — два разных запроса. Даже если AI уверен, он не выполняет финансовое действие. Уточнение необходимо, когда неясно, оплачена ли продажа, кому она относится или к какому долгу относится погашение.

## Минимальные проверки backend

Использовать тестовую PostgreSQL для транзакционных случаев: SQLite не подтверждает корректность блокировок PostgreSQL.

1. Продажа 3 000, оплачено 1 000 → долг 2 000.
2. Доплата 500 → продажи 3 000, поступления 1 500, долг 1 500.
3. Два одновременных погашения по 1 000 при остатке 1 500: только одно успешно, второе получает конфликт; остаток не отрицателен.
4. Повтор одного подтверждения с тем же ключом → тот же operation ID; новый ключ с уже использованным draft → дубль не возникает.
5. Один ключ с разными телами → 409.
6. Отмена доплаты → долг 2 000; затем отмена исходной продажи → нулевой долг. Повторная отмена невозможна.
7. Владелец A не читает и не изменяет данные B даже с известным UUID.
8. Невалидный AI JSON, timeout и неизвестный клиент не создают операций.
9. Операция у границы местной полуночи попадает в правильную дату отчёта.
10. Сетевой повтор обращения не дублирует заявку; заявка не меняет финансовые суммы.

## Передача результата

Дай команде URL, экспорт OpenAPI, тестовые аккаунты через закрытый канал, команды запуска, seed и список работающих методов. В репозитории — `.env.example` только с именами/заглушками, миграции и короткий README. Укажи фактические ограничения и дополнения, которые не успели войти.

Если времени не хватает, убираются Telegram, редактирование каталога, CSV и AI-напоминания. Денежная корректность, разграничение точек и подтверждение черновика сохраняются. Frontend №4 помогает с тестовыми фразами и воспроизведением ошибок; frontend №3 берёт на себя сборку и публикацию web, чтобы не перегрузить тебя.
