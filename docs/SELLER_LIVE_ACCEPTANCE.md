## Два локальных процесса

Для backend нужны Python 3.12/uv и согласованный серверный `.env`, полученный безопасным каналом. Для frontend — Node.js 22.12+ или 24. Не переносить DB/AI секреты в Vite env.

Терминал 1, из проверочной копии:

```powershell
cd apps/api
uv sync --locked
# Использовать свой игнорируемый .env; не заменять готовый файл.
uv run alembic current
# Для общего qadam-demo: 0003_drafts. Не выполнять seed/upgrade/downgrade/очистку.
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Backend `ALLOWED_ORIGINS=["http://localhost:5173","http://127.0.0.1:5173"]`. В отдельном `apps/web/.env.local` только публичные значения:

```dotenv
VITE_API_BASE_URL=http://127.0.0.1:8000/api/v1
VITE_SUPABASE_URL=https://pdjjdqgoitnkpgkbqjtp.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<publishable key проекта>
```

Терминал 2:

```powershell
cd apps/web
npm ci
npm run generate:api
npm run check:api
npm run typecheck
npm run dev -- --port 5173 --strictPort
```

Точное обновление типов — [описание и patch](../packages/contracts/FRONTEND_TYPES_UPDATE.md). OpenAPI — `http://127.0.0.1:8000/openapi.json`, Swagger — `/docs` без префикса `/api/v1`. API Base URL содержит этот префикс.

**Оба процесса и браузер должны работать на одном компьютере**, если используется `127.0.0.1`. Чужой localhost недоступен с компьютера frontend-разработчика. Если API запускается на другом компьютере, капитан отдельно передаёт достижимый адрес и разрешает точный origin frontend; заменить `VITE_API_BASE_URL` и перезапустить Vite. Общего HTTPS API пока нет, публикацию эта инструкция не выполняет. Не выдавать URL Supabase за URL FastAPI.

## Сценарий в браузере

Использовать два заранее созданных учебных Supabase-аккаунта A/B, привязанных к demo-точкам. Email/пароли передаются безопасным каналом. Publishable key и старый access token не заменяют вход. Не сохранять network HAR/trace/video/скриншоты формы с учётными данными; не копировать JWT в отчёт.

1. Открыть `http://127.0.0.1:5173/login`, войти A через email/пароль, не выбирать «Посмотреть демо». Ожидать `/seller`, живой режим, успешный `/api/v1/me` и шесть точек в селекторе.
2. Выбрать `mart-demo-clothes`, UUID `ad6203bc-7320-5b36-982b-135504c5af68`, открыть «Клиенты». Найти имя нового учебного клиента; перед повтором проверить, не был ли он уже создан.
3. Нажать верхнюю кнопку «+ Новый клиент». В пустом результате поиска есть ещё одна одноимённая кнопка — при автоматизации выбрать конкретную кнопку. Ввести явно учебное имя, заметку; контакт оставить пустым. Ожидать POST customers → 201, contact=null, balance_minor=0 и запись в списке.
4. Переключиться на другую свою точку — нового клиента там быть не должно. Вернуться на исходную — клиент виден.
5. Перезагрузить страницу. SDK должен восстановить реальную сессию и вызвать `/me` без повторного ввода пароля. При необходимости снова выбрать mart-demo-clothes: сохранение выбранной точки между reload не заявлено. Найти того же клиента с тем же UUID, без повторного создания.
6. Выйти. Переход на `/seller/customers` должен вернуть к `/login`. Войти B обычной формой; ожидать три точки, ни одна не принадлежит A. Поиск созданного A клиента не должен вернуть запись. Подстановка `?business_id=<точка A>` не должна переключать UI на чужую точку.
7. Отдельная проверка API с сессией B: GET клиентов точки A должен вернуть 404, а не список/данные A. В автоматизации использовать текущую сессию только в памяти; ничего не писать в логи. Это API-проверка, даже если fetch выполнен из браузера.
8. Выйти B и войти A: снова шесть своих точек, ранее созданный клиент доступен в исходной точке. Затем выйти. Учебного клиента оставить; денежные записи этот сценарий не создаёт.

Ожидаемые businessId и полный контракт — [инструкция подключения](BACKEND_FRONTEND_CONNECTION.md). Тестовый прогон может оставлять только явно учебных клиентов. Не очищать общую Supabase и не запускать на ней pytest.

## Границы результата

Вход, создание клиента, перезагрузка и смена аккаунтов проверяются через настоящие элементы интерфейса. Контроль `/me`, ответа POST и запрета чужой точки подтверждается реальными HTTP-ответами без перехвата/mocks. Проверка reload не доказывает автоматический refresh после естественного истечения access token — для этого нужен отдельный длительный сценарий. Не считать этот тест проверкой отсутствующих денежных/AI-страниц.

Фактический результат 2026-10-15: **PASS**, один живой сценарий с 10 контрольными точками. A/B/A входили обычной формой; новый клиент сохранился после reload; изоляция точек и отдельный API 404 подтверждены. В Supabase остался один явно учебный клиент, денежных операций не добавлено (5 → 5). Пароли после проверки удалены из локального `.env`; trace/HAR/video/screenshots не создавались. Подробности и ограничения — в последней секции [backend handoff](handoffs/backend.md).
