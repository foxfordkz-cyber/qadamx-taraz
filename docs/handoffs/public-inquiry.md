## Согласованный интерфейс и файлы

Капитан явно утвердил: автор заявки меняет `features/inquiry`, отдельные тесты и этот handoff. Владелец витрины меняет ShopPage, каталог и подключение. Внешних callbacks нет.

Из `apps/web/src/features/explore/ShopPage.tsx`:

```tsx
import InquiryForm from "../inquiry/InquiryForm";

<InquiryForm
  key={b.id}
  businessId={b.id}
  businessName={b.name}
/>
```

Оба props обязательны. `businessId` — UUID открытого магазина из API, единственный источник адресата. `businessName` используется только для отображения. Состояние сбрасывается по businessId внутри компонента даже без внешнего `key`; поздний ответ старого экземпляра игнорируется, его fetch отменяется. Имя магазина фиксируется для подтверждения конкретной попытки.

**Подключение блокирует общую сборку:** текущая main передаёт только `businessId`, поэтому `npm run typecheck` и `npm run build` сообщают TS2741 в `ShopPage.tsx:93`. Владелец страницы должен добавить `businessName={b.name}`. Это не скрыто optional prop, подавлением TypeScript или изменением чужого файла. Commit подключения от владельца пока не получен. Не сливать и не развёртывать этот Draft отдельно от подключения.

## Контракт и поведение

Проверены `apps/api/app/public_routes.py`, `schemas/__init__.py`, generated types, `packages/contracts/openapi.json`. Read-only GET работающего `https://qadamx-taraz.onrender.com/openapi.json` подтвердил API 0.6.2 и совпадение схем заявки/магазина и маршрута с этой базой. ZIP пользователя содержит тот же код формы/магазина/API и OpenAPI.

Используется **только** существующий `POST /api/v1/businesses/{id}/inquiries`:

```json
{
  "client_request_id": "44444444-4444-4444-8444-444444444444",
  "visitor_name": "Synthetic visitor",
  "contact": "synthetic@example.test",
  "message": "Synthetic request"
}
```

Все три пользовательских поля обязательны, trim + лимиты 100/200/2000. Контракт допускает непустую строку контакта, поэтому дополнительного телефонного/email regex нет. Поле контакта допускает телефон/email/Telegram: текстовая клавиатура с `enterKeyHint`, отключёнными автокапитализацией/исправлением; не принуждает к цифровой клавиатуре, которая скрывает `@`. У имени autocomplete name. Поля имеют required, видимые связанные ошибки и фокус первого ошибочного поля. Шрифт ввода не меньше 16px, кнопки не меньше 44px.

Публичный транспорт сохраняет credentials omit и redirect error. Авторизация продавца не передаётся. Успех появляется лишь после ответа с UUID `id` и датой со временем/часовым поясом `created_at`. Пустой/malformed/non-JSON ответ не считается успехом. Подтверждение называет магазин и номер заявки; срок ответа не обещается.

Синхронный ref-lock и disabled блокируют параллельные нажатия только в текущем экземпляре. За повтор одинакового сохранённого запроса отвечает **существующая серверная идемпотентность `client_request_id` внутри магазина**, а не кнопка. При сети, timeout 20 секунд, 408, 5xx, malformed success и 409 сохраняются исходные тело/ключ. Данные остаются читаемыми; повтор только явный и с тем же телом/ключом. Даже последующий 422/429 не снимает неопределённость предыдущей попытки. Автоповторов и нового ключа для обхода неизвестного результата нет.

При первом однозначном 4xx-отказе (кроме 408/409) ввод остаётся редактируемым, следующая попытка может иметь исправленное тело и новый ключ. После подтверждённого успеха отдельная кнопка начинает новую пустую форму. Ошибки не выводят raw server messages. Контакты не записываются в console, localStorage или sessionStorage.

## Backend-зависимости и границы

1. Базовая заявка не требует нового endpoint/поля/миграции. Существующая серверная реализация сериализует повтор по магазину, возвращает ту же квитанцию для одинакового тела и 409 при конфликте.
2. В InquiryCreate нет `product_id`/товара; автоматическая подстановка товара не реализована. Добавление структурированного товара требует отдельного backend-контракта.
3. Публичный магазин не содержит подтверждённых контактов продавца: кнопок звонка/WhatsApp/оплаты нет. Их появление зависит от реальных данных и контракта владельца страницы/backend.
4. Публичного lookup результата по client_request_id нет. Состояние повтора живёт только в памяти экземпляра, без хранения контактов. После закрытия/reload/перехода на другой магазин оно не восстанавливается; новый экземпляр/другая вкладка может создать новую заявку. Защита от дублей между такими действиями не обещается. Для безопасного восстановления после reload нужен согласованный публичный механизм backend; эндпоинт самостоятельно не придуман.
5. API-квитанция содержит id/created_at, без business_id: адресат определяется UUID маршрута запроса. Серверную изоляцию подтверждает только проверка backend с двумя владельцами, а не текст UI.
