## Recovery: результат и воспроизведение для Бекзата

Авторские customer/Auth тесты: **50 PASS** (32 + 18). Они проверяют same-key/body повтор, неизвестный результат, восстановление receipt после reload, A/B и business scopes. CustomerPicker и форма на странице теперь используют общий hook; повтор перед POST перечитывает intent из storage и сравнивает hash тела. На reload сохраняются key/hash, а не персональные поля; повтор допускается только после ввода совпадающего тела.

Добавленный review-тест **FAIL**: поздний успех после unmount стирает другой pending intent в том же scope:

1. Первая форма отправила K1, ответ POST задержан.
2. Форма размонтирована (переход страницы или смена сессии). Новая форма того же пользователя/точки получает completed receipt K1 и очищает его.
3. Пользователь отправляет следующего учебного клиента K2; ответ потерян, lookup not_observed. K2 сохраняется как unknown.
4. Приходит старый HTTP 201 для K1. Старый `finish()` вызывает безусловный `localStorage.removeItem(storageKey)` и удаляет K2.
5. После reload исходного K2 больше нет; безопасное восстановление потеряно. Это блокер против потенциального дубля, а не доказательство дубля на общей БД.

Исполняемый регрессионный пример: [recovery-late-review.test.tsx.txt](reviews/recovery-late-review.test.tsx.txt). Скопировать в `apps/web/src/test/recovery-late-review.test.tsx` в ветке 9a3c868, выполнить `npm run test -- src/test/recovery-late-review.test.tsx`. Используются только заглушки, никакой реальной БД/учётной записи.

Нужно очищать только конкретный завершённый intent (compare-and-clear по key/hash), ограждать поздние callbacks поколением scope/mount и проверить несколько одновременно живых форм/вкладок. После исправления повторить Picker продажи → страница клиентов, logout/login A/B/A, reload и задержанные ответы. Вторую параллельную реализацию не создаём.

Дополнительный риск review: `loadCustomerIntent` безусловно переносит legacy key без API origin в текущий origin. При неизвестном происхождении legacy-запроса нельзя молча перепривязывать его к другому серверу. Требуется безопасный переход либо явная блокировка с инструкцией; это замечание по коду, не живая проверка другого хостинга.

## Исходный recording.webm и новая запись

Капитан подтвердил: исходный recording.webm отсутствует. Инцидент `d53a7f33-f768-4051-9a30-2dbfc6cbe915` невозможно точно воспроизвести. Другое успешное аудио не закрывает инцидент.

Инструкция для **нового** сценария на телефоне:

1. До записи записать язык, точную учебную фразу, продажу/оплату/долг в тенге; неизвестную оплату пометить «неизвестна», не нулём. Не использовать данные реальных клиентов.
2. Записать короткую фразу в диктофоне телефона и **сохранить/экспортировать исходный файл** (например, OGG, M4A или WebM), без пересжатия через мессенджер. Для браузерной записи сохранить файл из элемента аудио, если браузер предлагает скачивание; наличие такой кнопки на конкретном телефоне пока не проверено. Если скачать браузерную запись нельзя, не обещать воспроизводимость: использовать сохранённый файл диктофона через «Выберите файл» и отдельно проверить браузерный микрофон.
3. Сохранить файл и ожидания локально в закрытой папке, сообщить путь капитану; аудио не добавлять в Git и отчёты. Передавать только согласованным закрытым способом.
4. До отправки согласовать один платный прогон и бюджет. Затем один POST draft (не более одной STT и одного extraction), без повторов/fallback и без подтверждения денег. При неизвестном результате сначала изучить request_id/логи.
5. Зафиксировать request_id, модель, длительность, безопасные этапы transcript validation/extraction/schema/deadline/draft_save и сравнение чисел. Не публиковать аудио, речь, ключи, JWT или полный provider response.
